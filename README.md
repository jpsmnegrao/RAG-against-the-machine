# RAG-against-the-machine


## Description

This project's objective is to implement a Retrieval-Augmented Generation (RAG)
system that answers natural-language questions about the vLLM codebase and its
documentation. The system ingests the vLLM repository, chunks the source code
and Markdown files with two dedicated strategies, indexes the chunks with BM25,
retrieves the most relevant snippets for a given question, and generates a
grounded answer using a local language model (Qwen/Qwen3-0.6B). Retrieval
quality is measured with a recall@k metric based on character-range overlap
(IoU) against a ground-truth dataset, matching the metric used by the official
grading script (the moulinette).

### Tests

The project uses pytest to test its core functionality, including:
- Chunking: chunk size limits, text offsets, supported file types, and invalid inputs.
- Indexing: BM25 index creation, corpus collection, and index export.
- Search: query handling, retrieval edge cases, and missing indexes.
- Answer generation: dataset processing, missing source files, and generation
  failures.
- Evaluation: input validation, malformed datasets, and Intersection over Union
  (IoU) calculations.

Tests cover normal operation, edge cases, and error handling to help ensure the pipeline behaves reliably when inputs or required files are invalid or missing.

### Instalation

Important: When on the school PCs (or other lower spec machines) the project
must be installed using the provided Makefile commands rather than running uv
directly.

The Makefile sets project-specific environment variables for UV, Hugging Face,
and PyTorch caches. Running uv commands directly does not load these variables
and causes caches to be stored in the user's home directory. On the school's
computers, this consistently leads to storage issues during installation and/or
execution.

To install run:

`make install`

## Additional sections:

### System Architecture

The pipeline is split into independently testable stages, each living in its
own module under src/:

```
data/raw (vLLM repository)
        │
        ▼
 [ chunker.py ]      extract_corpus_files() walks the corpus (.py, .md, .txt)
        │            chunkinizer() dispatches each file by extension
        │            file_chunker() splits it into IndexedChunk objects
        ▼
 [ indexer.py ]      chunk_collector() orchestrates the corpus walk + chunking
        │            bm25_scorer() tokenizes chunk text and builds a BM25 index
        │            index_exporter() pickles the index + chunks to data/processed/
        ▼
 [ search.py ]       load_search_artifacts() reloads the persisted index
        │            search() / search_dataset() score a query against the
        │            index and return the top-k MinimalSource results
        ▼
 [ answer.py ]       retrieve_sources() re-reads the exact character span for
        │            each retrieved source, builds a grounded prompt, and
        │            calls Qwen/Qwen3-0.6B to generate an answer
        ▼
 [ evaluate.py ]     compares a StudentSearchResults file against a
                     ground-truth AnsweredQuestions dataset and reports
                     recall@1 / @3 / @5 / @10
```

All data exchanged between stages is validated through the pydantic models in
schemas.py (MinimalSource, UnansweredQuestion, AnsweredQuestion, RagDataset,
MinimalSearchResults, MinimalAnswer, StudentSearchResults,
StudentSearchResultsAndAnswer), plus one project-specific extension,
IndexedChunk, which pairs a MinimalSource with the actual chunk text so the
indexer has something to tokenize.

Everything is exposed through a single CLI built with fire (src/__main__.py),
with tqdm progress bars on every long-running loop (chunking, tokenizing, batch
search, batch answering).

### Chunking strategy

Two chunking strategies are implemented in chunker.py, both built on top of
langchain_text_splitters.

- RecursiveCharacterTextSplitter:

1. Python (.py) — uses RecursiveCharacterTextSplitter.from_language with
Language.PYTHON, which prefers splitting at class/function boundaries before
falling back to blank lines, single lines, and finally raw characters if a
block still exceeds the configured size.

2. Markdown (.md) — the same splitter with Language.MARKDOWN, which prefers
headers and paragraph breaks as split points.

3. Plain text (.txt) — a generic RecursiveCharacterTextSplitter with no
language-specific separators.

All three strategies are capped at max_chunk_size characters (default 2000,
configurable via --max_chunk_size on the index command), with a chunk_overlap
of max_chunk_size // 10 so that content straddling a split point is not
entirely lost from both resulting chunks. Each chunk keeps its exact
first_character_index / last_character_index in the source file (via the
splitter's add_start_index option), so the offsets reported to the grader
always slice back to precisely the chunk's own text.

### Retrieval method

Retrieval uses BM25, implemented with the bm25s library:

- bm25_scorer() tokenizes every chunk's text with bm25s.tokenize() in a single
  call (so the whole corpus shares one vocabulary), then builds a bm25s.BM25
  index from the tokenized corpus.
- search() / search_dataset() tokenize the query the same way and call
  BM25.retrieve() to get the top-k ranked chunks, which are mapped back to
  their MinimalSource metadata (file path and character range).
- the index and the chunk list are persisted together as two pickle files under
  data/processed/ (index.pkl, corpus.pkl), so search can reload both without
  re-chunking or re-tokenizing the corpus.

BM25 was chosen over plain TF-IDF because it normalizes for chunk length and
applies diminishing returns to repeated term occurrences, both of which matter
given the corpus mixes short and long chunks.

### Performance analysis

Measured against the public reference datasets (100 questions for docs and 99
for code), verified against the official moulinette:

| Metric | Docs questions | Code questions |
|---|---:|---:|
| Recall@1 | 61.0% | 32.3% |
| Recall@3 | 78.0% | 45.5% |
| Recall@5 | 83.0% | 55.6% |
| Recall@10 | 91.0% | 59.6% |

Both required thresholds are met with margin (docs Recall@5 ≥ 80%, code
Recall@5 ≥ 50%). Code questions score lower than docs questions, which is
expected: BM25 is a lexical matcher, and a natural-language question rarely
shares vocabulary with the identifiers and syntax of the code that answers it.

Indexing the full vLLM corpus (1969 files, 14638 chunks) completes in well
under a second on the tested machine, comfortably inside the 5-minute budget.
Batch retrieval over 100 questions also completes in under a second,
comfortably inside the 90-second budget for the almost 200 questions.

Answer generation is the slowest stage and has no documented time budget in the
subject. On the campus machine's GPU (a very small, ~3.6 GB card), generation
ran into out-of-memory errors at full precision and only limited improvement
under 4-bit quantization; CPU-only generation was also slow.
enable_thinking=False (disabling Qwen3's default <think> reasoning trace) gave
the single largest speed improvement during development. The current generation
time per question is not something the subject requires to fall under any
particular threshold, since the only documented performance requirements
concern indexing and retrieval.

### Design decisions

1. Library-based chunking over a hand-rolled AST splitter. An AST-based chunker
(using Python's ast module) was prototyped first, to understand the underlying
problem of correctly slicing top-level functions/classes and computing
character offsets from line numbers. Once the offset-slicing logic was
understood, chunking was rebuilt on top of RecursiveCharacterTextSplitter,
since the grading metric's IoU threshold (0.05) does not require precise chunk
boundaries and the library already implements a sensible recursive fallback for
oversized blocks.

2. A single pickle file pair for the index. Chunks and the BM25 index are
persisted together (chunks built once, tokenized in the same order, never
reordered independently) so that BM25's positional result indices always map
back to the correct chunk metadata.

3. `evaluate` re-implements the moulinette's own logic, not a simplification of
it: same file-path exact-match rule, same IoU ≥ 0.05 overlap rule, same
recall@1/3/5/10 reporting, so it can be used for real iteration before running
the official moulinette.

4. Graceful degradation over hard failures. Missing index files, missing source
files, malformed dataset JSON, and empty/gibberish queries are all handled so
the CLI never terminates with an unhandled traceback; retrieval and generation
instead report what happened and return an empty or explanatory result.

### Challenges faced

1. Small-GPU hardware constraints on the campus machine. The GPU available on the
school PC has very little VRAM (~3.6 GB), which caused out-of-memory errors
when loading the model at full or half precision. 4-bit quantization,
dtype="auto", and disabling sampling were all tested; only disabling the
reasoning trace (enable_thinking=False) produced a meaningful, reliable
speed-up. This was treated as a hardware ceiling rather than a code defect,
since the subject does not set a time budget for answer generation.

2. Keeping character offsets consistent through library-based chunking. Since
the actual chunking work is delegated to RecursiveCharacterTextSplitter, care
was taken to only rely on its start_index metadata (rather than re-deriving
offsets independently) so that first_character_index / last_character_index
always match raw_text[start:end] exactly — verified directly with unit tests.

### Example usage

### 1. Index the vLLM repository under data/raw/
`uv run python -m src index --max_chunk_size 2000`

### 2. Search a single query
`uv run python -m src search "How to configure the OpenAI server?" --k 10`

### 3. Batch search a whole dataset of questions
```
uv run python -m src search_dataset \
    --dataset_path data/datasets/UnansweredQuestions/dataset_docs_public.json \
    --k 10 \
    --save_directory data/output/search_results/UnansweredQuestions
```

### 4. Generate a grounded answer for a single question
`uv run python -m src answer "How to configure the OpenAI server?" --k 10`

### 5. Generate answers for a whole batch of search results
```
uv run python -m src answer_dataset \
    --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
    --save_directory data/output/search_results_and_answer/UnansweredQuestions
```

### 6. Evaluate retrieval quality against ground truth
```
uv run python -m src evaluate \
    --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
    --dataset_path data/datasets/AnsweredQuestions/dataset_docs_public.json
```
